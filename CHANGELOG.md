# Changelog

All notable changes, newest first. Upgrade steps are in [UPGRADING.md](UPGRADING.md).

## Unreleased

- **A Claude Code session that joins during a turn can be woken when that turn ends (#437):** a session whose start was not seen and whose join could not bind its process, such as every hand join on a linked device, used to get its wake route only at its user's next prompt. Now the end of the turn it joined in, or its idle notification, binds the session's process as that prompt would, locally and on a linked device, so an ask can wake it without a new prompt. Such a callback may take the 400 ms start budget when it binds. Codex sessions still get their route at the next prompt.
- **Linked-device wake advice agrees everywhere (#445):** a request to a member its linked device will try to wake now reads `next: "the linked device will try to wake it"` in `--json`, not `waits for its next crosshall command`. The home also sends `why: "linked_device"` with the `device` outcome, so a v0.4.0-rc.1 or rc.2 client prints `not woken: linked_device` instead of a blank reason; the outcome and the daily count are unchanged. `crosshall owner start` lists a member that runs on a linked device apart from those nothing can wake, and says why it gets no resume notice: startup resume notices require a local session.

- **The release gate's full-run row says what ran beside it:** when the row fails, its detail names the failed tests instead of the log's last line, which was often macOS's launch-denial report. ci-checks prints that report on any failure, and the same denials occur in passing runs. The detail also gives the load before and after the run, and counts the other test runs on the machine (the lock serializes full runs only) and the processes an earlier row left running. `row_full_run.others` lists each of them (#391).

## v0.4.0-rc.3 (2026-11-27)

- **Upgrading:** v0.4.0-rc.1 and v0.4.0-rc.2 stores stay on schema 37. The first start from v0.3.1 backs up the store and upgrades it from schema 30 to 37. See [UPGRADING.md](UPGRADING.md#to-v040-rc3).
- **A notice with nothing left to read no longer holds its member until the owner resumes it (#446):** when a Codex thread notice is reported as no longer queued and the member has read everything it carried, the dispatcher frees the member's lane. The settled event records `not pending: nothing left to read`, and the member's next notice is sent instead of `not woken: an earlier notice is unobserved`. A notice that still carries unread work stays held, and the owner is still alerted. The dispatcher log now notes, once per notice, a withdrawal that ended not pending or unreachable.
- **The owner sees why a linked member has no wake route yet (#437):** `crosshall owner who` adds `no notice route: its session start was not seen` for a member on a linked device that joined after its session started and has sent no prompt since. As for a local member, its next prompt opens the route.
- **The home no longer says a linked member has no notice route while its device can wake it (#438):** `who`, `ask` and `reply` on the home said `not woken: no notice route` for a member on a linked device even when the device woke it. While the device holds its event stream and the member's launch could be woken, they now say `the linked device will try to wake it` (`wake: device` in `--json`), with no advice to wake the member by hand: only the device can check its session's route. A held wake, an offline device and a member with no launch the home could wake are reported as before. The daily report still counts these sends as `send.wake.none`.
- **Link confirmation discards queued terminal input (#439, #442):** `crosshall link` clears input queued on the terminal before asking for confirmation. If the link is declined, the error quotes the answer, including an empty answer.

## v0.4.0-rc.2 (2026-11-27)

- **Upgrading:** a v0.4.0-rc.1 store stays on schema 37. The first start from v0.3.1 backs up the store and upgrades it from schema 30 to 37. See [UPGRADING.md](UPGRADING.md#to-v040-rc2).
- **Linking a device is available by default (#400, #436):** from the owner's terminal, run `crosshall link <ssh-target>` to join another device's hall. Use `crosshall link status` to see the current connection and `crosshall unlink` to return to the local hall.
- **Linking again after a home rollback stays with the same hall (#418, #435):** `crosshall link` refuses to replace a stopped profile when its SSH target now reaches a home serving another hall, before it asks for confirmation or sets the stopped store aside. A dispatcher that starts during a link change no longer removes that change's new enrollment record.
- **A linked display receipt can arrive after its session ends (#434):** the home confirms a receipt captured before the session ended, even if the end reached the home first. The membership stays departed.
- **A linked wait keeps its first cursor after a lost reply (#433):** the home recovers the original cursor when the device retries the first poll, so the wait still sees work that arrived in the gap. If the home cannot recover the cursor, it directs the member to its inbox.
- **A linked device catching up holds a bounded backlog (#422, #432):** the home writes at most four pages of events ahead of what the linked device has acknowledged, so a device reconnecting to a large backlog no longer queues all of it in memory while it applies the events one by one.

## v0.4.0-rc.1 (2026-11-26)

- **Upgrade from v0.3.1:** the first start backs up the store and migrates it from schema 30 to 37; no setup is needed. Linking a second device stays experimental, behind `CROSSHALL_EXPERIMENTAL_LINK=1`. See [UPGRADING.md](UPGRADING.md#to-v040-rc1).
- **`crosshall wait` on a linked device (#400):** a session on a device linked with `CROSSHALL_EXPERIMENTAL_LINK=1` can wait. Each poll goes to the home as one short read-only call, so the home shows the member as woken by its wait and the wait ends on the home's message as it does at home. Between polls nothing holds the link, and other commands from the device go through as usual. A home of an earlier build refuses the wait as not available on a linked device yet.
- **Hooks run on a linked device (#400):** a session's hooks on a device linked with `CROSSHALL_EXPERIMENTAL_LINK=1` answer from the device's event cache. The home's adapter policies reach the device in its event stream when both sides negotiate the new `policy` capability, so a device of an earlier build never receives them (home migration 037 records which stream did); while the cache is current the device publishes them for its hooks, and removes them first when the cache stops counting, so hooks go quiet instead of acting on an old policy. A prompt shows the notice offer the home prepared for that member, and the hook's written acknowledgement suppresses it on the device and confirms it at the home. Session starts, prompts, turn ends, approvals and session ends are kept in the device's spoke store, sent to the home in each session's hook order with the token each hook took under its publish lock, and removed once the home recorded them, also across reconnects. A hook fired right after `join` or `join --move` counts, even before the home's event for that change reached the device. Repository auto-join, turn-end asks, reach and join hints, and hook routes stay off for members of a linked device. Spoke migration 005 adds the device's policies, its hook outbox and where each session's stamp last changed. Spoke migration 007 records, per session, the highest hook sequence already released to the home. A hook handled after a higher one went out (a later pass, a clock that stepped back, or a packet processed again after a restart) is dropped instead of making the home stop that session's hooks. A display receipt is always sent, even late: the home confirms its notice without moving the session's hook order. Frames queued before the upgrade take their generation from their token. A session registered again starts its marks over. A native hook (no linked device) takes no token.
- **A linked device keeps the home's event stream (#400):** the device's dispatcher holds the stream on a second SSH connection of its own, so member commands keep their plain call and answer exchange. It records each member's scope and the notice offers the home prepared in its spoke store, with their leases, and acknowledges every event only after it committed. A change to a member applies under that session's hook publish lock, and the acknowledgement names the publish sequence it applied at, so the home can order the session's later hook facts after it. A reconnect resumes from the acknowledged event; a new dispatcher process, a device reboot or a gap asks for a snapshot, and nothing cached counts until one applied. Hooks on a linked device answer from this cache (see below). If the home device is restored from an older backup, the linked device notices its stream went back, applies nothing of it, and refuses every command with `home_rolled_back` until `crosshall link <home>` runs again, which enrolls the device again on a fresh device store (the old one is kept aside); sessions then join again, and the home admits each one's first command without the stamp the old store held.
- **Linked-device events on the home device (#400):** the home serves a resumable stream of member selections, invalidations and prepared notice offers for authenticated links that negotiate events. It records scoped hook facts and written receipts, withholds turn-end asks from linked members, and retains no remote host paths in the stream. Migration 034 adds the home event log and its cursors.
- **`crosshall retry <key>` on a linked device (#400):** after a command's outcome was reported unknown, it shows what the hall did with it, looking it up without running it when the device does not know yet. When the hall has no receipt, the command will never run under its key, though it may have run before its receipt expired: retry then sends it again once, under a new key, as a new operation that may repeat its effect, and a repeated retry shows that resend's outcome instead of sending another. On the hall's home device it is refused with a next step.
- **A linked device's own sessions work in the home's hall (#400):** on a device linked with `CROSSHALL_EXPERIMENTAL_LINK=1`, `join`, `who`, `inbox`, `read`, `ask`, `reply`, `note`, `log`, `leave` and `focus` go to the home over the link. The device registers its sessions in its own store, under `spoke/` in the state directory, one per hall and device, with member spools apart from the local hall's, so `crosshall unlink` finds the local hall as it was. A keyed command is recorded before it is sent: if the link ends before the answer, the member gets `outcome_unknown` with its key, and the device looks the command up on the next connection without running it again. Hook facts of a linked device reach the home over the event stream (see below).
- **A linked device can ask what became of a command whose answer it lost (#400):** `crosshall link serve` accepts a `receipt` frame naming the request exactly as the device sent it, and answers with the committed receipt, or with `link_outcome_unknown` after fencing the request's key in the same transaction, so the request never runs if it reaches the home later. A lookup runs nothing and changes no session registration, selection or pickup. The home admits a forwarded request only under the device's admission generation that its link was handed before the device was welcomed; the retention pass that deletes a device's fences raises that generation in the same transaction, so no request held on an earlier link of that device outlives its fence, whatever the clock does, and other devices' links carry on. Migration 033 adds the admission generation and the fences of sessions the home does not know yet, which are pruned with operation records.
- **Codex managed-daemon notices on Intel macOS.** Crosshall ships publish evidence for Codex 0.172.0 with `codex-1`. The native run verified request and reply delivery in both directions with Claude Code using scratch evidence, plus suppression while a Codex server approval is open. [Intel macOS run](https://github.com/BeomSeogKim/crosshall/actions/runs/45745791324/attempts/2).
- **The home device runs the member commands of a linked device, behind the same opt-in (#400):** `crosshall link serve` accepts a `call` frame, which carries a member command the device authenticated against its own session, and answers with the hall's result. The home checks, in one transaction, that the link's device credential is still current (enrolling a device again closes its old links), that the command comes from the device's current registration of that session, and then returns an already committed receipt for the same operation before checking the member's channel, so a retry after a lost answer is never run twice. Only `join`, `who`, `inbox`, `read`, `ask`, `reply`, `note`, `log`, `leave` and `focus` are forwarded, without process, takeover or repository arguments, and the home never probes a process or reads a leaf for these members. Owner restore and takeover refuse members of a linked device. Migration 032 adds the device-scoped keys.
- **Experimental spoke transport (#400):** set `CROSSHALL_EXPERIMENTAL_LINK=1` and run `crosshall link <ssh-target>` to enroll a second device through OpenSSH. `crosshall link status` shows the negotiated version and connection state as the spoke reconnects. `crosshall unlink` restores the spoke's local hall. Member commands on the spoke are forwarded to the home (see below).
- **The home side of a hall on two devices, behind an opt-in (#400):** with `CROSSHALL_EXPERIMENTAL_LINK=1`, `crosshall link enroll --name <device>` records a device on the hall's home device and reads its secret on stdin, and `crosshall link serve` speaks the link protocol on stdin and stdout: a handshake that checks the hall, the device's proof of its secret and a common link version, then pings. The spoke starts both commands through the user's own SSH. Migration 031 adds the `hall` and `device` tables. The dispatcher keeps each device secret in its store, makes the home's proof and checks the device's itself, and no audit or replay record holds a secret; during enrollment the secret passes through a private owner spool packet (mode 0600), as every owner command's arguments do.
- **Codex explains when the hall cannot wake it.** A join or first prompt names a missing managed app server and how to reopen it. A hand join with no reported route also points the user to `/hooks` to check trust.

## v0.3.1-rc.1 (2026-11-26)

- **Upgrade from v0.3.0.** The first start backs up `store.sqlite3` and migrates schema 29 to 30. To roll back, restore the schema 29 backup and reinstall v0.3.0. See [UPGRADING.md](UPGRADING.md#to-v031-rc1).

- **Codex managed-daemon notices on Linux arm64:** Crosshall ships publish evidence for Codex 0.172.0 with `codex-1`. An offline run with the official CLI packages verified one idle wake and settled reply, no wake during server approval, and native request and reply delivery in both directions with Claude Code using scratch evidence (#384).
- **Uninstall removes what setup created after an agent edits its settings:** Claude Code writes its settings file after setup, for example when you pick a theme at first run. Uninstall could then no longer restore the file byte for byte, and it left the empty hook lists, the empty `permissions.allow` list and the `autoMode.allow: ["$defaults"]` list that setup had created. Setup now records the lists and objects it creates, and uninstall removes each one that is empty once crosshall's entries are gone, with `"$defaults"` when it is the last item of an allow list setup created. The agent's and the owner's own settings stay. An install made by an earlier version has no such record: after an edit, its uninstall still removes only crosshall's entries. (#385)
- **Assigning a prompt to its turn no longer reads the launch's whole history:** at every prompt, Stop and idle report, the hall folded all prompts, Stops and idle reports of the member's launch into turns, so a long session paid more for each hook as it went on: 4.3 ms per prompt at 1,000 turns and 12 ms at 3,000 in a domain measurement. Migration 030 records on each launch the newest observation the last fold read and the dispatcher's time then. The next fold starts at the latest turn before anything it has not read, and starts with the typed-ahead turns still running there; it stays about 0.45 ms at 3,000 turns. It folds every fact, as before, when that start could give other turns: no record yet, a fact that names an earlier turn, a running placeholder a turn-end notice keeps, or a dispatcher clock that went back past a fact the last fold read. A retention pass that deletes a launch's facts or turns clears its record (#366).
- **The race detector runs nightly:** a scheduled workflow (also started by hand) runs the tests of `internal/dispatch`, `internal/appserver`, `internal/publish` and `internal/store` with `-race` on main every night. On a pull request it would add about seven minutes, because every store open runs migrations through the pure-Go SQLite, which is 14 to 25 times slower under the race detector.
- **The /tmp cleaner no longer turns hooks off at midnight:** macOS's daily `/tmp` cleaner removes a file once its access, change and modification times are all more than three days old, and reads after the first do not renew the access time. So it removed `policy`, `repo-defaults`, `turn_end` and `builds` about three days after the dispatcher wrote them, in use or not. Until it also removed `ready`, which makes the dispatcher republish everything, every hook was off for that moment. The dispatcher now renews the times of these files every hour, and republishes any of them that is removed anyway, with one log line (#378).

## v0.3.0-rc.1 (2026-11-25)

- **Antigravity hooks see prompts and turn ends (manifest `agy-2`):** `crosshall setup antigravity` now installs `PreInvocation` and `Stop` beside `SessionStart` in crosshall's group. A joined Antigravity session sees the pending line at the first model call of its next prompt, once per prompt however many model calls follow. Its `Stop` takes part in the turn-end check, and the release ships tested evidence for Antigravity CLI 1.5.16 interactive sessions on macOS arm64 (`internal/publish/agy_evidence.go`, registered without a publish adapter, so Antigravity still has no notices); only a turn's first Stop that ends with no tool call pending and no background work can continue it, once. Antigravity CLI runs hook groups in name order and, once a Stop hook continues a turn, skips the later Stop hooks for that Stop; the install question names a group in the same file that sorts after `crosshall` and has Stop hooks. An `agy-1` install shows as drift until `crosshall setup antigravity` upgrades it; going back below this release needs the uninstall step in [UPGRADING.md](UPGRADING.md). An opt-in conformance test (`CROSSHALL_CONFORMANCE_AGY=1`, billed) drives real Antigravity turns and writes the evidence.
- **CI checks a new build's hooks under the previous build's dispatcher:** on Linux, CI builds the pull request's base (on main, the previous main) and v0.2.0, from before prompts could name their server. For each, the end-to-end suite installs it, starts its dispatcher, replaces the binary the hooks name with the new build and checks that the new hooks stay fail-open under the running older dispatcher, as after an upgrade in place: prompts are recorded, nothing about the other build reaches the session, and a note sent across the upgrade is read (#252). Locally the check runs for each of `CROSSHALL_E2E_BASE_BINARY` and `CROSSHALL_E2E_RELEASE_BINARY` that names such a build.
- **Publish evidence and reach reasons sit with their adapters:** each adapter's shipped evidence moved from one list in the core to a file beside the adapter (`internal/publish/claude_evidence.go`, `codex_evidence.go`, which now holds the Codex 0.172.0 daemon row), with every build key, result reference and run date unchanged. A session an adapter's sender cannot reach (`codex runs without its daemon`, `codex daemon not confirmed`) is classified where that adapter's own `Reach` reports it, as `no_route` for that adapter, instead of by a test of Codex's name or of the reason's words: a new adapter needs no edit outside its own files, two adapters may use the same wording, and a core reason such as `route not proven` keeps its class whatever an adapter declares. Stored reasons, the evidence seed, owner precedence and every output are unchanged.
- **Finding a member's latest fact no longer reads its whole launch:** a prompt with work to offer read every observation of the member's launch twice, so a Claude Code prompt that showed a pending line took longer with each turn (#366). That read now starts from the newest turn and the newest facts, through three indexes the dispatcher adds to the store when it starts; the schema version stays 29, and a test compares the pick with the old full read on random histories. In the dispatcher alone, such a prompt at about 1,100 turns took 18.1 ms before and 4.8 ms after. Reassigning the launch's turns still reads all of its prompts and Stops, so the prompt still grows with the launch, more slowly (part 2 of #366).
- **The first prompt of a resumed session shows work that came while it had no launch:** a request stored while a member's session had no open launch (its start hook missed, as under load) marked nothing for the session's hook, and the first prompt of its next process answered from its old stamp without the pending line; the request showed only at the prompt after. A prompt that binds a launch whose start was missed now always asks the dispatcher for its line.
- **A hook manifest can describe a vendor whose prompt callback runs per model call and whose turn end names no turn:** an event can answer at once, with no dispatcher request, when the callback's fields do not match (`when`); read integers and booleans as the vendor sends them (`literal_fields`); name its turn by another field (`turn_field`), record it as the session's open turn (`open_turn`) and give it to a Stop (`turn_from_open`); tell repeated Stops of one turn apart (`ref_fields`); offer a continuation only for Stops with given field values (`stop_require`); read whether a continuation runs from a declared field (`stop_active`); and answer a Stop with `{"decision":"continue","reason":...}` (output `continue`). A manifest with `build_from_host` takes a launch's vendor version from the build `crosshall setup` recorded for the executable that runs the hook, and its mode from that executable's arguments. When that executable changes, the dispatcher reads `--version` again from the recorded path only, never one a hook names, and doctor says so until it has. Shipped manifests do not use these fields yet; their hooks behave as before.
- **Codex managed-daemon publish evidence:** the release ships evidence from a real Codex 0.172.0 daemon on macOS arm64 with `codex-1`. Other macOS arm64 `codex-1` daemon builds inherit this coverage unless their own evidence or a build stop takes precedence. The trial verified one idle wake and settled reply, plus suppression while an approval is open. The installer discloses notice costs and publish settings per adapter.
- **A Codex session whose start was missed gets its notice route from its next prompt:** when a Codex session's `SessionStart` missed its deadline, its first prompt joined it but registered no notice route and recorded its mode as unverified, so notices never reached it and senders read `not woken` until the session started again (#252). A Codex prompt run by the managed app server now names that server and its home, as a start does. When the recovering prompt names its server, the dispatcher keeps the prompt's mode, takes the prompt's time as the session's start, and registers the route the start would have; the route is then proven against that server as a started session's is. A member recovered this way before the upgrade gets its route at its next start. A dispatcher that does not offer `prompt_host` in its ready marker gets prompts without these fields, so a new hook under an older dispatcher works as before.
- **Antigravity CLI 1.5.16 identifies its sessions without a warning:** an Antigravity session names only its language server build, `cli-<release>`, and crosshall never took that for the CLI release, so every Antigravity member saw `identity variable unverified on agy: CLI version unknown`. The language server build of 1.5.16 matched `agy --version`, so the manifest now says the build names the CLI release and verifies 1.5.16. Every other build keeps the warning.
- **The adapter-name guard covers the whole core:** it now also scans the dispatcher, the generic publish code, identity and the store, and flags SQL text that names an adapter in quotes. The only allowed case is the approved `TurnEndClaude` telemetry key. The release's own reminder measurements for Claude Code and Codex moved from setup's shared code into their installers; doctor and setup show the same evidence.
- **Native cross-vendor release check:** Claude Code and the Codex managed app server exchange requests and replies through native notices in both directions using loopback models. The release gate requires both directions.
- **A fresh adapter ID proves adapters need no core edit:** a fixture adapter built in only under the `synthadapter` build tag (a manifest, an identity row and an installer in its own files) installs beside the owner's hooks, enrolls, is identified, gets a request at its next prompt, follows owner policy and uninstalls byte for byte through the normal entry points. CI runs it, and checks that nothing outside its files names it. Shipped builds do not contain it.
- **An adapter bundle built in under a build tag can add itself without a core edit:** the hook manifest reader also reads manifests that a tagged file of the bundle adds (a shipped manifest of the same name wins), the identity index test checks every compiled manifest so a bundle's identity row can be a tagged file, and setup installs an adapter that has no member command permissions instead of refusing it. Shipped builds read, install and identify as before.
- **Codex notices go through the app server, can be taken back, and a Codex approval is confirmed by its server:** the Codex adapter now has a sender. A notice is queued on the member's thread with `thread/queue/add` over the managed server's control socket, written only after the socket's listener is proven to be the server the route named, and tagged with the attempt's identity; never with `turn/start`, which steers a working turn. The client is written on the standard library's `net` alone and can send only `thread/read` and `thread/queue/add`, `list` and `delete`; it never answers a request from the server, since any client there can answer a pending approval. A Codex member stays `candidate (no tested evidence for codex-1 on <platform> daemon)` until evidence for its build ships, so this build still sends no Codex notice by default; `owner who` reads that reason instead of `no sender for codex`. A submitted notice whose turn would find nothing (its session ended, or everything in it was read, offered in a prompt or is gone) is withdrawn from the thread's queue through the home's proven server and settled with a `publish_attempt_settled` event (`withdrawn: ...`); a notice that is no longer queued, or a server that cannot be reached, keeps the member's lane until the receipt or the owner's `crosshall owner publish resume`, so no second notice follows one that may still run. A Codex approval request that has stood two seconds is checked with `thread/read`: when the thread waits on its owner's approval, the hall stores it as an open approval, so a send reads `not woken: its turn waits on its owner's approval`, `owner who` shows the owner line, and it is checked again before its 30-minute cap instead of aging out. No schema change.

- **Usage statistics, asked once:** with a yes, the dispatcher sends one report a day of rounded counts and fixed words about whole UTC days after the answer, through `/usr/bin/curl`, the first request for a new report at most once per 24 hours (a retry of the same bytes may come sooner) and nothing older than seven days. `crosshall owner telemetry show` shows the report waiting to be sent, exactly as it will be sent, and `crosshall owner telemetry` names the receiver's last answer and the next attempt. Hooks and member commands make no network call, and the binary links no TLS code, so a hook's start time does not change. `crosshall owner telemetry off` and `/etc/crosshall/telemetry-off` stop it before the next request, and the environment opt-outs stop a dispatcher started with them. [Every field](docs/telemetry.md). Reports go to `https://telemetry.addylog.dev/v1/report`; a build not made from a release tag neither asks nor sends (#222, #223, #231, #234).
- **No end-of-turn check where the hall reaches you:** a session the hall can start a turn in is told so at a prompt, and then ends a turn that showed no pending line without a `crosshall read`. When the hall stops reaching it, the next prompt says so and the check applies again. The database moves to schema 19 (#121).
- **Upgrade:** the database moves from schema 18 to 21. Budget rounds are only recorded; nothing is enforced by them yet (#230). See [UPGRADING.md](UPGRADING.md#to-v020-rc2).
