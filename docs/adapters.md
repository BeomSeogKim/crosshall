# Claude Code, Codex CLI and Antigravity CLI adapters

Adapters are optional hooks. crosshall works without them: a member that runs the commands itself follows the same rules.

## Setting up

In your own terminal, run `crosshall setup status` to check whether Claude Code, Codex or Antigravity CLI is on PATH. It shows each adapter's configuration path, hook installation state and policy, and reports any drift or pending recovery. Add `--json` before `setup` for machine-readable status.

A crosshall binary replaced without running setup again leaves the hooks of the earlier manifest revision on disk. `crosshall owner start`, `crosshall owner doctor` and `crosshall setup status` then say so in one sentence that names both revisions and the command, for example `The Claude Code hooks on disk were installed for claude-2; this crosshall installs claude-3. Run crosshall setup claude.` It appears only while setup's own hook entries are on disk, its record names another revision, and a hook this binary installs is missing. In JSON, the adapter's `installed_rev` in doctor and in `setup status` is the revision setup recorded, and doctor's `warnings` carry the sentence.

`crosshall setup codex` pins the selected crosshall state directory in its hook commands, so use that directory for member commands in the same `CODEX_HOME` and a separate `CODEX_HOME` for each independent state directory.

`crosshall setup` shows the detected vendors, absolute settings paths, and exact command rules. One approval installs the listed hooks and rules. A decline in manual setup applies only to that run. Use a named setup command to limit the plans to particular vendors. Setup preserves existing command approvals. In Codex, review and trust the installed hooks with `/hooks`.

Claude Code uses `$HOME/.claude/settings.json` by default and Codex uses `$HOME/.codex/hooks.json`. Set `CLAUDE_CONFIG_DIR` or `CODEX_HOME` to an absolute directory to select another location. Antigravity uses the shared `$HOME/.gemini/config/hooks.json`, where Crosshall owns its named hook group. Codex and Antigravity hook commands pin the Crosshall state directory selected when you install them. [Google's Antigravity hooks documentation](https://antigravity.google/docs/hooks/#managing-hooks-in-antigravity-cli)

The user-level command rules cover routine member commands such as `read`, `reply`, and `wait`. The rules for the bare name `crosshall` trust the agent's PATH to select the executable. Claude Code and Antigravity CLI also match the installed absolute path. Claude Code stores the rules in the settings file's `permissions.allow` array. Antigravity CLI uses `permissions.allow` in `$HOME/.gemini/antigravity-cli/settings.json`.

On supported Claude Code builds, the same setup approval adds a rule to `autoMode.allow`. It covers direct calls to those member commands, including display-only pipes into `head` or `tail` and `2>&1`. When setup creates the allow list, it includes `"$defaults"` to keep Claude's built-in rules. When the list already exists, setup preserves its contents and defaults behavior. Claude's explicit ask and deny rules and classifier hard blocks still take precedence. Run `claude auto-mode config` to see the effective rules. [Claude Code auto mode settings](https://code.claude.com/docs/en/auto-mode-config#override-the-block-and-allow-rules)

Codex loads `rules/crosshall.rules` inside the selected Codex home when it starts and runs allowed commands outside its sandbox. Setup declares the installed `crosshall` path as a Codex host executable. Codex applies the same command rules to the bare name and the resolved absolute path, preserving existing bare-name prompt and forbid rules. Setup still installs hooks when it finds an existing user rule that may declare the `crosshall` host executable or when the binary has been renamed. The preview shows why command permissions are skipped.

To revisit one vendor, run `crosshall setup claude`, `crosshall setup codex` or `crosshall setup antigravity`. An owner-run script can preview and apply the named vendors in two commands.

```sh
crosshall setup --dry-run claude codex
crosshall setup claude codex --apply
```

`--apply` reads no input. For a new setup, it installs the named vendors' hooks and command rules. When it resumes an interrupted setup for the same vendors, it applies the previously approved edits.

With input or output redirected, `crosshall setup claude` previews the plan, while bare `crosshall setup` prints the scripted form and exits with code 2.

## Joining a repository's channel

Hooks run for every session of that agent under your user account, in every repository. Run `crosshall owner channel default demo` in a repository to have new sessions there join the channel `#demo` at startup. If the project has no channel assigned, a new session gets a one-line prompt to join its team's channel with `crosshall join <channel>`. The join output shows its assigned `@alias` and the roster. Repository defaults apply to a session's first enrollment. Later hooks respect the session's selected channel, including one selected by `crosshall join <channel> --move`.

With automatic joining on, a session that starts in the work tree of a Git repository with no channel gets the repository's own channel. crosshall creates it at that start, names it after the repository's directory (`#shop-api`; a name already in use gets `-2`), makes it the repository's default and joins the session. Installing an agent's hooks turns automatic joining on, as the install plan says, unless you already set it; `crosshall owner channel auto off` and `on` are yours to change at any time, and a later install keeps your choice. A directory Git does not accept as a repository gets no channel. A session inside Git's own directories (`.git`, or wherever the repository keeps them) is in no repository: it creates nothing and joins nothing, also when the repository has a default channel. Linked worktrees belong to their repository and share its channel, also when the repository keeps its Git directory elsewhere. A default you set in the repository's main checkout is the repository's and wins; one you set in a linked worktree is that worktree's and wins there. Outside Git nothing is created and such a start prints no line. `crosshall owner channel auto off` stops creating channels; a repository that already has one keeps it. The switch is off until you turn it on.

An unenrolled Claude Code or Codex CLI session can join on a later prompt when its `SessionStart` and the prompt are in the same repository; linked worktrees count as one repository. This also works when the owner sets the default channel after the session starts. A resume, clear or compaction before enrollment follows the same repository rule. A session that starts elsewhere and enters the repository later can join with `crosshall join <channel>`. If it ends before enrollment, its next start counts as a first start.

A Claude Code start can miss the hook's deadline, for example on a loaded machine. The session's next prompt then does what the start would have done: it ties the session to its Claude Code process, under the same checks as a `crosshall join` typed in that session, and the hall can start its turns from then on. This also brings back a member whose resumed start was missed. When the checks fail (the hook runs in another PID namespace, another member holds the process, or the member left by hand), the session joins as before and the hall reaches it only at its prompts; `crosshall owner who --all` then says `no notice route: its session start was not seen`, and `crosshall owner doctor` counts such members. A start hook that never ran leaves nothing to recover: the session joins at its next start, or with `crosshall join`.

In Claude Code, `/clear` gives the conversation a new session ID in the same process. That session stays the same member, wherever the member joined: it keeps the alias, the open requests and the owed replies, and its start tells it who it is and what is pending; the old session ID is retired. This needs the member's process to be known: its start in that process (the first start or a resume), or a `crosshall join` run inside the running session, which binds the process when it still runs and no other member runs in it. A session started inside a member's tool shell is its own conversation and never takes that member. If the process's member left by hand or the owner removed it, `/clear` joins nobody, and neither does the new conversation's first prompt; a `crosshall join` there is the explicit join, and later clears follow the member it made. After an owner restore, a `/clear` in the old conversation's process does not take the member back. The conversation before the clear, resumed later, is told which member it was cleared into; `crosshall join <channel>` makes it a new member, and a join that fails changes nothing.

A hook tells a session it joined one line: its alias, its channel and who else is there (`[crosshall] Joined #shop-api as @claude1, with @codex1.` and the command that prints the member rules). A session that is alone in its channel is told nothing; it gets the line at its first start or prompt after someone else has joined. The member rules come with the session's first crosshall command (any but `wait` and `leave`), so a session that never takes part never carries them. Antigravity has only a start event: a conversation that is alone at its start gets no line and learns who it is from its first command.

If a join committed before its hook could deliver the line, the next eligible hook delivers it. Once a hook delivered it, or a command printed the rules, later prompts omit it.

The hook checks membership immediately before writing the line. A write already in progress can finish after the member leaves.

Antigravity's adapter (manifest `agy-2`) handles the CLI's `SessionStart`, `PreInvocation` and `Stop` with a single workspace and a CLI conversation path. `SessionStart` supplies startup context and can join the workspace's configured channel. The CLI calls `PreInvocation` before every model call; only a prompt's first call shows the prompt line, so a turn with several model calls gets it once. `Stop` takes part in the turn-end check where tested evidence covers the build; only a turn's first Stop that ends with no tool call pending and no background work can continue it. The CLI's `/hooks` command shows the installed events. Antigravity members still use the normal inbox and wait commands for incoming work. Antigravity has no Crosshall publish or idle wake.

Antigravity CLI 1.5.16 runs the hook groups of a hooks file in the order of their names, not their order in the file, and when one Stop hook continues the turn it runs no later Stop hook for that Stop. A group whose name sorts after `crosshall`, such as `owner`, misses a Stop that Crosshall continues and runs at the turn's next one; a group whose name sorts before it, such as `aaa-owner`, runs first and sees every Stop. Setup names this in its install question when a later group has Stop hooks. A turn the user cancels with Esc reaches no Stop, so it is not checked.

An Antigravity member is tracked through its `agy` ancestor process from its first crosshall command, whether it joined by hand or through the startup hook: when the CLI exits, the member departs. The launch the startup hook records does not change this, because no Antigravity hook ends it. `/clear` keeps the same CLI process, so an older conversation stays joined until the CLI exits. A process with another name, such as the IDE's language server, is not tracked; the owner departs such a member by hand. See [when a member goes quiet](operations.md#when-a-member-goes-quiet).

Codex CLI 0.171.0 can run commands through a shared app server. The server can stay alive after a client exits and serve a later client, so it is not a Codex member's host. Codex's hooks give no launch ID, so its session end is recorded but departs nobody: a Codex member's exit is not tracked, and the owner departs it by hand or it leaves by itself. More than twelve hours after its session ended, with nothing seen from it since, `crosshall owner who` reports it, and `crosshall owner depart --ended` departs it when it has no open request.

## The turn-end check

When a turn ends with an unread request, a supported adapter continues that turn once with the `[crosshall] pending:` line. Claude Code receives the line as Stop hook context; Antigravity CLI receives it as the reason of a `continue` decision. Each request is announced this way once and stays unread in the inbox. Each continuation costs one more model request. A Stop waits for the dispatcher only while such a request may exist; a turn with none ends without that wait. The binary ships tested evidence for Claude Code 2.1.330 on macOS arm64 in print and interactive mode. It ships tested evidence for Antigravity CLI 1.5.16 on macOS arm64 in interactive sessions (manifest `agy-2`). The adapter must be enabled, the running build and mode must be verified, and the session must match the evidence. Stock Codex sessions cannot be verified for this check. The owner turns the check off for one agent kind, leaving joining, the prompt line and notices as they are, with `crosshall owner adapter set claude --turn-end off`; `--turn-end on` or `default` turns it back on. Neither turns the check on for a build its evidence does not cover. The switch applies from the next turn end and does not restart sessions.

To record evidence for another Claude Code profile, work from the release checkout with `claude` and Go on PATH. Print mode (`claude -p`) and interactive sessions use separate evidence.
1. Create an output directory outside your home and resolve its physical path, so it contains no symbolic link: `out="$(cd "$(mktemp -d)" && pwd -P)"`.
2. Run `CROSSHALL_CONFORMANCE_OUT="$out" go test -tags conformance -count=1 -run '^TestClaudeCodeTurnEndConformance$' ./test/conformance` for print mode, or the same command with `'^TestClaudeCodeInteractiveTurnEndConformance$'` for interactive sessions. The run uses temporary homes and a local stand-in for the model, so it makes no billed requests. The interactive run starts a real `claude` on a pseudo-terminal of its own and types into it; it opens no window and touches no session of yours.
3. Import the file it writes to `"$out"` with `crosshall owner adapter evidence <file>`.
4. Turn the adapter on with `crosshall owner adapter set claude --enabled on`.

For an Antigravity CLI build, run `CROSSHALL_CONFORMANCE_AGY=1 CROSSHALL_CONFORMANCE_OUT="$out" go test -tags conformance -count=1 -run '^TestAntigravityInteractiveTurnEndConformance$' ./test/conformance` on macOS with `agy` on PATH and signed in, then import the file the same way and turn the adapter on with `crosshall owner adapter set agy --enabled on`. Unlike the Claude Code run, it drives real Antigravity turns against Google's model with your sign-in, so it makes about twelve billed model calls. It works in a scratch workspace with its own hall; your global hooks file and settings stay as they are.

`crosshall owner doctor` lists tested turn-end evidence and reports availability for current sessions, including the source version when they inherit evidence. Its count measures committed continuation claims. Evidence covers the same vendor, platform, mode and manifest revision. An exact-version entry takes precedence, so an exact `candidate` or `unavailable` entry keeps the check off for that build. If the vendor's hook callback format changes and requires a new manifest revision, run the conformance test again and import its evidence.

In an interactive session the check also covers a turn whose prompt was typed ahead, while the turn before it was still running. Stock Codex sessions cannot be verified, so the check stays unavailable for them.

In Claude Code, a prompt typed while a turn is running is its own turn: it gets its prompt line, and its Stop gets the check. Hook callbacks that reach the dispatcher out of order are placed by the times their hooks recorded. A Stop that arrives before the prompt that opened its turn cannot be checked, because its hook has already returned. A Stop that arrives before a prompt typed ahead during its turn is checked as the latest turn's, as far as the dispatcher knew then.

Claude Code 2.1.330 takes a prompt typed while a tool runs into the running turn instead: the model gets it beside the tool result, and it gets no turn or Stop of its own. Its prompt callback looks the same, so the hall cannot tell it apart at the time. Manifest `claude-3` therefore also installs the Notification hook for `idle_prompt`, which Claude Code sends when a session has waited for input for about a minute. That report closes the session's open typed-ahead turns, ends an unknown notice suspension recorded before it (timed or lasting, recorded as a `publish_suspension_lifted` event), and a notice with nothing observed since it counts as the session's own turn. It costs one hook run per idle period and no model request. It is not shown as presence: `who` keeps showing the last turn's Stop.

## The prompt line

At a prompt, a joined session can see a `[crosshall] pending:` line with unread message IDs. The hook confirms the IDs after it writes the whole line. If the hook times out before writing, the next eligible prompt can show the same unread IDs. A crash after writing, overlapping prompts, or a busy dispatcher can repeat a line until the dispatcher receives confirmation. Repeats do not pick up work, open a model turn or repeat the turn-end announcement. A turn-end announcement or an observed publish notice also keeps those IDs off later prompt lines.

An older hook or dispatcher counts a prompt offer when the dispatcher prepares it. After an upgrade, a current hook can show still-unread IDs from before the upgrade again.

After a compaction or `/clear`, work the session was already told about comes back as one count, `[crosshall] 2 unread, 0 owed. Run crosshall read.`, and after `/clear` the session is also told its alias and the command that prints the member rules. `crosshall who` shows the last observed event and its age. Claude Code sends no event when a permission dialog is answered No, so after a denied dialog `who` shows the approval request until the session's next prompt. When two prompts are queued while one turn runs, Claude Code merges them into one request: a pending line that arrived between them is not in that request and shows at the next prompt or command instead. Codex observations carry the label `unverified`, as every adapter's still do. Only a publish notice, where a route is available, wakes an idle session.

A session the hall can start a turn in is told so once, at a prompt: `[crosshall] The hall brings new work to this session: no check is needed before ending a turn.` While that was the last word, a turn that showed no `[crosshall] pending:` line ends without the `crosshall read` of rule 1: work that arrives during the turn gets a turn of its own. The hall says it while the session's notice route is available, or while a notice queued for it is less than ten minutes old (the dispatcher notices the ten minutes passing within a quarter of a second). When that stops (an absorbed notice, a stopped build, the hourly cap, an owner or member publish switch, or a start that registers the route again), the next prompt says `[crosshall] The hall cannot reach this session now: check before ending a turn (crosshall read).`, and the first line comes back when the route does. A line counts as said only once the hook has printed it; one that was lost is offered again. A session in do not disturb gets neither line, and a session with no supported notice route, such as Antigravity CLI, Claude Code in print mode or Codex running without its daemon, gets neither line. A prompt with nothing new keeps the hook's fast path: when what the session was told no longer holds, the dispatcher marks the session so that its next prompt asks once.

## Publish notices

With an adapter's hooks installed, the hall can tell a session about new work without the session polling. It writes one line to the agent's own message route (for Claude Code, the session's messaging socket, which its `SessionStart` hook reports; if the start ran before the socket existed, the session's next prompt or Stop reports it):

```text
[crosshall] pending: 12 15. This notice is from crosshall, not from a Claude session. Run crosshall read, then use crosshall reply to answer or decline each request it shows, as the member rules say.
```

The dispatcher waits while the session reports a current prompt or permission request. When the turn ends, or its report expires, the dispatcher checks which messages still need a notice. It skips IDs whose prompt-line output the hook has confirmed. If an item is picked up, its request is closed, or the hook confirms its prompt line after reservation but before submission, the dispatcher releases the batch and selects the items that still need a notice. If the session becomes busy after submission starts, the vendor can queue the notice for a later turn. The session runs `crosshall read`, which picks the work up. The notice carries message IDs only, never a body or a peer's words. Claude Code (seen on 2.1.329) shows it to the person as a message from another session, inside its own wrapper paragraph. The notice says what to do with the work. The v0.2.0-rc.4 text ended `: do not reply to the sender. Run crosshall read.`, and in a recorded run a Codex model read the request and then neither answered nor declined it (#288). A notice written with that text before an upgrade still counts as a notice.

The binary ships tested publish evidence on macOS arm64 for interactive Claude Code 2.1.330 with `claude-2` and interactive Claude Code 2.1.331 with `claude-3`. It ships evidence for managed Codex 0.172.0 in `daemon` mode with `codex-1` on macOS and Linux, both arm64 and amd64. Other builds with the same adapter, platform, mode and manifest revision inherit that evidence, subject to exact-version evidence and build stops. Sessions outside that coverage continue to use the prompt line or `crosshall read`.

A Codex notice is queued on the session's thread in its managed app server (`thread/queue/add` over the server's control socket), and the server starts the turn when the thread is idle. A Codex session's hook reads the process that runs it. When that is the managed app server of the session's `CODEX_HOME` (`codex app-server ... --managed-daemon`, which Codex starts by default), the session's route is recorded with the server's release as its version and `daemon` as its mode, at its `SessionStart` or on a prompt that recovers a missed start. A `SessionEnd` closes the route. Codex sends that end about a minute after the terminal closes. A session that runs its own server, as "Run without daemon this time" does, is recorded as `in_process`, and `owner who --all` says `publish: candidate (codex runs without its daemon)`; when the hook cannot read its host, or a daemon start did not name the server's process, it says `codex daemon not confirmed`. Every `SessionStart` decides again, so a thread resumed without the daemon loses its route. A daemon start also names the server's process and its home. The sender publishes only after the dispatcher has checked that the same process still runs as the managed server, from the release directory of the `CODEX_HOME` that `crosshall setup codex` installed the hooks into, and it writes to the control socket only when the socket's listener is that process. It sends only `thread/read` and `thread/queue/add`, `list` and `delete`, and never answers a request from the server. A queued notice whose turn would find nothing, because the session ended or everything in it was read, is withdrawn from the queue; one that is no longer queued keeps the member's lane until its receipt or `crosshall owner publish resume`. A Codex approval request is checked with `thread/read`, and only one its server shows waiting on the owner counts as an open approval. A Codex launch is never a verified one; that check takes its place, and a Codex build that inherits tested evidence is confirmed, stopped and resumed like any other. One notice at a time is open per Codex thread in its home, so members on one server do not hold each other's notices. A Codex notice reads `... not from a Codex session ...`, and the receipt for it is matched on the thread it was sent to.

A route publishes when all of these hold:

1. The session has a current route. Claude Code also requires a verified launch. Tested evidence covers the adapter, platform, mode and manifest revision. Exact-version evidence overrides inherited evidence. [Conformance](../CONFORMANCE.md#publish-profiles)
2. The dispatcher proved the route against the session's process. For Codex, that proof identifies the managed server whose control socket will accept the notice.
3. The route was activated. Only messages stored after that moment are offered, so a backlog never arrives as a burst.
4. No switch is off, the session is not in bypass permission mode, and the route is not suspended, capped or held.

What a member sees:

- A send reports `stored -> notice queued` when submission has started or the notice can be queued now. If a running turn defers the notice, an accepting [wait](waiting.md) gets priority. Otherwise, a covered turn-end check offers up to 10 unread requests in ID order. Their senders see `it sees this when its turn ends`. For other eligible work, including final replies, the sender sees `the hall checks again after its turn`. When a request or final answer needs a manual wake, the result also names the recipient: `next: nothing will wake @sol. Ask a member the hall can wake (crosshall who), or tell your user.`
- The reason is one of a fixed set, with no binding ID or owner command: `no notice route` (also a route that cannot carry a notice, such as a Claude session whose socket no hook has reported since it joined or moved; `no notice route for codex` when the agent has no sender, or a Codex CLI session is not confirmed to run in its managed app server), `notices not proven for its build`, `notices suspended` (`until 14:32` when the suspension has an end), `notices off` (a switch, or do not disturb), `its session ended (it may be closed)` (its last session ended and none has started since; a Codex session end is also reported for a thread its app server unloaded, so the window may still be open), `notice limit until 14:32`, `an earlier notice is unobserved`, `device offline` (a linked device's wake stream closed and its route otherwise qualifies), `a turn is running`, `its turn waits on its owner's approval (asking again cannot help)`, and `a note starts no turn`. In `--json` each recipient carries `wake` (`notice`, `wait` or `none`), `why` (`no_route`, `unproven`, `suspended`, `off`, `capped`, `held`, `turn_open`, `awaiting_approval`, `kind`, `session_ended`, `device_offline`), `adapter` with `no_route` in those two cases, `seen_at` (`turn_end`, `prompt` or `command`) and `until_ms`. A deferred notice has `why=turn_open` and omits `seen_at` unless the turn-end check offers the request. Its `next` field describes the check that will run.
- `crosshall who` shows the same words per member: `woken by a notice`, `woken by its wait` or `not woken: <why>`, and `crosshall waiting` shows them, as of when it runs, for each recipient that has not picked a request up or asked for more time and has no notice for that request; a request that has one shows its notice state. While a reservation awaits submission, a running turn can defer it and the request then shows the current wake prediction alongside the reservation. A request a prompt line or a turn end already showed, and that the member has not read, says `shown 14:32, not read` there instead of where it will be seen, since each request is shown once; JSON gives `shown_at_ms` and no `seen_at`. JSON keeps `publish` with the state word: `off`, `candidate`, `available`, `held`, `suspended` or `capped`.
- `crosshall waiting` shows each notice behind a request: submitted or not, and whether the session's hook observed it.
- **A turn that waits on its owner's approval.** When a Claude Code member's latest fact is a shown permission dialog (`Notification` with `permission_prompt`), only its owner can move the turn. Within the fact's 30-minute cap a send says `not woken: its turn waits on its owner's approval (asking again cannot help)` (`why=awaiting_approval`), `crosshall waiting` says `waits on its owner's approval since 14:32` instead of the last observed fact, `who` says `approval requested 3m ago, waits on its owner`, and the hall sends no notice into that turn. `crosshall owner who` starts with one line per such member, `@opus in #dev waits on your approval (requested 3m ago); open requests: #7.`, and `crosshall owner doctor` warns of each. JSON carries `approval_open: true` on the observed fact. A denied dialog sends no Stop, so past the cap the hall claims nothing: notices and the manual-wake advice come back as before, and the dialog stays on show, hedged: `asked its owner for approval 40m ago, no answer reported` (in `waiting`, `who`, `owner who` and doctor). It ends with the member's next fact (its Stop or a new prompt), its next crosshall command, the end of its launch (a session end, or its process known gone) or its departure. Codex also runs its `PermissionRequest` hook for escalations it approves on its own. A Codex request opens the same approval wait only when the managed server confirms that the thread is waiting for its owner. A self-approved escalation keeps its ordinary `approval requested` fact.
- `crosshall publish off` stops notices to your own session, and `crosshall publish on` allows them again; `on` never overrides an owner's off.

What the owner controls:

| Command | Effect |
| --- | --- |
| `crosshall owner publish hall on\|off` | Notices for the whole hall |
| `crosshall owner adapter set <adapter> --publish on\|off\|default` | Notices for one agent kind |
| `crosshall owner adapter set <adapter> --turn-end on\|off\|default` | The turn-end check for one agent kind; it still needs evidence for the build |
| `crosshall owner publish member <binding-id> on\|off\|default` | Notices for one member; this switch beats the adapter's, which beats the hall's |
| `crosshall owner publish resume <binding-id>` | Lift a member's automatic suspension and any stop of its current build, and release a notice of its that has no receipt |

`crosshall owner who --all` and `crosshall owner doctor` show each member's reason. Doctor also shows the publish status of each live build and the day's notice outcomes per adapter. It splits the day's unknown receipts by the condition that kept each from being the session's own turn: `open placeholder` (the last turn is a prompt typed ahead that has not finished; on Claude Code 2.1.330 this usually means a prompt typed while a tool ran, which Claude Code took into the running turn, so it never gets a Stop of its own; with manifest `claude-3` the session's idle report closes it about a minute after the turn), `unfinished turn` (the last turn had no Stop, and another turn's activity came after it), `activity since stop` (something happened after the last turn's Stop), or `no turn but facts` (the session had no turn since it started, only other hook facts). Unknown receipts recorded before this was kept count as `cause not recorded`. A member suspended by an unknown receipt shows the same cause in its line, for example `suspended: notice 11 unknown (open placeholder)`. For a build inheriting evidence with fewer than three confirmations, doctor counts notices that entered submission and remain held without a receipt.

The hall stops by itself, toward pull, in these cases:

- **Held.** A notice was written but the session's hook has not reported it. Nothing more is sent to that session until the notice is observed, the session's process ends, or the owner releases it with `crosshall owner publish resume <binding-id>`. A timeout frees nothing, but a notice held for 15 minutes is reported to the owner (see [operations](operations.md#loop-guard)).
- **Suspended.** An absorbed or unknown notice suspends notices for its session for 30 minutes. So do three consecutive failed submissions. A third active suspension for the same launch lasts until that launch ends if all three came from absorbed notices or failed submissions. Expired suspensions and unknown receipts are excluded from that count. An own-turn receipt or an owner resume resets the count. When the session is told it lost reach because of a lasting suspension, its own line gives `crosshall owner publish resume <binding-id>`. The owner is also told directly, on the desktop and on the next owner command (see [operations](operations.md#loop-guard)). For a version inheriting tested evidence, an absorbed or unknown notice before the first three own-turn receipts also stops publish for that build. Resume lifts the build stop and keeps the confirmation count. A newer tested evidence import for the exact version also lifts the build stop.
- **Capped.** A member gets at most 30 notices an hour.

After the dispatcher starts, a member that owes a reply that no notice will carry, because the member already read the request or was told of it by a notice or its prompt line, or because it came before the route, gets one resume notice, once per start, when its turn is free within the first hour:

```text
[crosshall] pending: 2087 2090. This notice is from crosshall, not from a Claude session. The hall restarted and you still owe these requests: run crosshall read 2087 2090 to see them again, carry on, and use crosshall reply to answer each, ask for more time or decline, as the member rules say.
```

It follows the same route rules as any notice, and its echo counts as its receipt. One that is not submitted is tried once more five minutes later; once one is submitted, or after the second try, the member gets no other until the next start. Each is recorded as a `publish_resume` event with its binding, attempt and requests. `crosshall owner start` prints one line when members owe replies, for example `3 members owe 4 open requests: 2 can be woken and get one resume notice when their turn is free; 1 cannot be woken (@sol in #dev: no notice route for codex).`

A notice is an offer, not a delivery: the message is already stored, and a notice that is lost or ignored leaves it unread for `crosshall read`, the prompt line or a wait.

## Turning adapters off and removing them

`crosshall setup off` disables adapter effects and leaves the settings in place. Use `crosshall uninstall codex`, `crosshall uninstall claude` or `crosshall uninstall antigravity` to remove an adapter's managed hooks and command rules. Bare `crosshall uninstall` covers all adapters. In a terminal, uninstall asks before starting a removal. Bare `crosshall uninstall` uses the previous approval when resuming an interrupted removal. With input or output redirected, it previews the removal. Add `--apply` to remove the managed entries without reading input. When a settings file is as setup left it, uninstall restores its original bytes. After the agent or the owner has changed the file, uninstall removes the managed entries and every list or object setup created for them that is then empty, and keeps the rest of the file. A Claude `autoMode.allow` list that setup created goes too when only its `"$defaults"` is left. Uninstall reports any entries it leaves for manual review. See [removing Crosshall](operations.md#removing-crosshall) for binary and state removal.

## What doctor reports

For each vendor version, platform and mode, `crosshall owner doctor` reports capabilities as `tested` (passed a conformance check), `candidate` (awaiting verification) or `unavailable` (unsupported), with `unknown` when evidence is missing.

There is no reply reminder in this release; `crosshall setup --dry-run` and `crosshall owner doctor` list it as `parked`.

For each adapter, doctor reports recorded hook starts, helper timeouts and missed deadlines for the current UTC day. A callback's deadline is 150 ms from its start, except a session start and a prompt that enrolls or repairs its session or binds the launch of a missed Claude Code start, which get 400 ms, and a prompt that does none of these keeps 150 ms; the vendors' own hook timeout is 1 s. A callback counts as having missed its deadline when it took its budget or longer, or ran out of time after 150 ms. It shows `hook counters unknown` when it has no records for that adapter that day.
